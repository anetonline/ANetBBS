# ANetBBS v1.1.56 — Fix a real sudo escalation outage for the Service Control Center (October 2026)

**If your Install/Restart/Backup buttons are currently failing with a sudo "no new privileges" error, the web upgrade button cannot apply this release** — it depends on the exact privilege escalation this release fixes. Download the tarball and run `sudo bash update.sh` over SSH instead; after that one manual update, the web buttons work normally again, including for every future update.

Fixes a real live production outage: the Service Control Center's web-triggered restart, upgrade, and backup actions (all of which escalate privileges via a narrowly-scoped sudo grant) could silently stop working on an install that has the systemd sandboxing hardening directives applied to `anetbbs-web.service`, with `sudo` reporting "The 'no new privileges' flag is set, which prevents sudo from running as root."

Root cause: several of those hardening directives (`SystemCallFilter=`, `RestrictNamespaces=`, `ProtectKernelTunables=`, `ProtectKernelModules=`, `ProtectKernelLogs=`, `MemoryDenyWriteExecute=`, `RestrictRealtime=`, `LockPersonality=`) each implicitly force systemd's `NoNewPrivileges=yes` unless it is explicitly overridden with `NoNewPrivileges=no` — a documented systemd behavior this project's own unit files never accounted for. Simply omitting the directive, which every version of the `anetbbs-web.service` unit until now did specifically to keep sudo working, was never actually sufficient.

Fixed by explicitly setting `NoNewPrivileges=no` for `anetbbs-web.service` in both `install.sh` and `update.sh`'s unit generation, and by adding a dedicated, self-healing step to `update.sh` that writes this override to any existing install automatically on the next update — no manual intervention required for installs that already picked up the hardening directives before this fix existed. Also fixes the `/admin/preflight/` diagnostic page's own sudo-escalation check, which previously only inspected the unit file's raw text and could report a false "ok" in exactly this situation; it now queries systemd's own computed effective configuration instead.
