# ANetBBS v1.1.58 — Correct fix for the sudo escalation outage (October 2026)

**This supersedes v1.1.56 and v1.1.57's fix for the sudo "no new privileges" error — both of those releases shipped a fix that did not actually work.** If your Install/Restart/Backup buttons are currently failing with that error, this release still cannot be applied through the web upgrade button itself, for the same reason as before. Apply it manually: download the tarball and run `sudo bash update.sh` from an SSH session.

v1.1.56 added an explicit `NoNewPrivileges=no` to the web service's systemd unit, believing that would override the implicit force several other hardening directives trigger. It didn't — confirmed on live production by restarting the service and reading `/proc/<pid>/status`, which still showed the kernel's privilege-block flag set despite the override. v1.1.57 then removed the directives that looked like the obvious seccomp-backed culprits, which also didn't fully fix it. A real bisection against the live production unit — each directive tested alone, through a real restart and a real `/proc` read, not reasoned about — found that `ProtectKernelTunables=`, `ProtectKernelModules=`, `ProtectKernelLogs=`, `ProtectClock=`, and `ProtectHostname=` each independently force the flag too, since each blocks a specific kernel syscall via its own seccomp filter layered on top of its mount/capability restriction. Only `PrivateTmp=`, `ProtectHome=`, `ProtectSystem=`, `ReadWritePaths=`, and `ProtectControlGroups=` are actually safe to keep on this one unit, which needs to retain the ability to escalate privileges via sudo. This release removes the five directives that were still silently breaking it, and corrects the admin Preflight Checklist page's guidance text to match.
